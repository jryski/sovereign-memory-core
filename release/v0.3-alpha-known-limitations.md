# Sovereign Memory v0.3-alpha known limitations

This document is part of the v0.3-alpha release gate. It states what the alpha
evidence does **not** establish so a green receipt is not expanded into a larger
claim later.

## Attribution is assertion-grade, not credential proof

Attention/provenance rows can carry `credential_ref`, but existing organic rows
may legitimately have it unset. On shared credential paths, the recorded actor
or source agent is therefore an assertion made through an accepted runtime path,
not cryptographic proof that a particular human/model held a unique credential.
Do not use v0.3-alpha attribution as non-repudiation evidence.

## Perimeter findings are bounded, not exhaustive

`perimeter-report/1` is a fail-closed release gate. `unsupported` is distinct
from clean, and the assertion seam refuses unsupported targets. When evaluation
is possible, however, the preserved predecessor assertion can short-circuit at
the first non-ACL category. The `findings` array is therefore not a census of
every simultaneously broken category. Absence of a category from `findings` is
not evidence that category passed. Repair a reported finding and rerun the gate.

## Provider-exit proof is a privacy-safe synthetic deployment slice

The v0.3-alpha provider-exit rehearsal proves the package/restore mechanism on a
representative synthetic source built from the exact reviewed migrations. It
does not export the private production PERSONAL or HOUSE datasets. A production
data export remains a separate operator act and must preserve the same privacy,
recovery and evidence boundaries.

## Database portability is not product portability

The package restores the PostgreSQL system of record. It does not claim to
recreate a hosted vendor's auth service, object storage, edge/serverless
functions, scheduler/cron, observability, billing, networking, dashboard, or
other control-plane features. Those services require separate migration plans if
a deployment depends on them.

## Supported provider-exit engine range is PostgreSQL 15/16

The v1 sovereignty manifest declares PostgreSQL major version `>=15` and `<17`.
The clean provider-exit rehearsal is run on PostgreSQL 16 and C1 is exercised on
PostgreSQL 15 and 16. v0.3-alpha does not claim that the bundle/restore path is
validated on PostgreSQL 17. A deployment running PostgreSQL 17 must use its own
version-matched recovery/acceptance procedure until that compatibility range is
expanded by reviewed evidence.

## The current bundle profile has two explicit representation constraints

The `full-synthetic-v1` proof profile records these constraints in its own loss
report rather than hiding them:

1. manifest v1 does not declare the non-deferrable cyclic self-foreign-key for
   attention-event supersession; restore orders revisions and verifies the
   lineage afterward;
2. enum-valued memory columns in the synthetic profile are migration-default
   invariants rather than relation payload fields.

The proof requires zero unclassified and zero unsupported loss for the declared
profile. These representation constraints are still limitations of the generic
v1 package format.

## Restore is a trusted operation

The provider-exit loader temporarily disables USER triggers on `public.memories`
while restoring already-recorded rows, then re-enables them before conformance
checks. This avoids replaying write-time event generation against historical
rows. The restore itself is therefore a privileged/trusted operation; the
post-restore checks are what prove that guards, RLS, lifecycle, provenance and
the C1 perimeter are armed again.

## Drift inventory is structural/textual, not semantic equivalence

`schema-drift-inventory/1` compares normalized `pg_dump --schema-only` output
byte-for-byte after removing only dump comments and randomized psql restrict
markers. It intentionally errs toward reporting drift. Equivalent SQL written
differently can compare unequal, and database comments are outside this drift
hash. Source and destination inventories should be captured with the same
`pg_dump` major version. A clean comparison means the captured executable schema
shape matched under this contract, not that two arbitrary SQL programs were
formally proven equivalent.

## SHA-256 checksums provide integrity, not authorship

Bundle and release checksums detect accidental corruption and unsynchronized
changes. They are not digital signatures. Anyone able to replace both an
artifact and its checksum can manufacture a matching pair. v0.3-alpha does not
claim signed provenance or non-repudiation for release artifacts.

## HOUSE acceptance is a separate deployment gate

Core CI and provider-exit evidence do not substitute for HOUSE acceptance.
HOUSE requires its own recovery anchor, exact deployed version, rollback-safe
acceptance battery and zero-residue verification. No v0.3-alpha release claim
should imply that HOUSE was mutated or accepted unless the separately recorded
HOUSE gate says so.

## Erasure outside the system of record is not proven

The alpha can remove or supersede state inside the modeled database boundaries,
but it does not establish physical erasure from every external backup, log,
cache, workflow artifact, third-party service, or operator copy. Claims about
data deletion must stay scoped to the systems actually measured.
